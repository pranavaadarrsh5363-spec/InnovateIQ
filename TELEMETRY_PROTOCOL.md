# InnovateIQ — Field Telemetry & Sensor Protocol Specification

This document defines the ingestion protocol, payload format, physical validation boundaries, regulatory evaluation rules, and edge gateway standards for the **InnovateIQ Platform**.

---

## 2. Ingestion Source Types

Every telemetry record ingested into InnovateIQ must declare an explicit provenance source:

| Source Identifier | Description | Required Metadata |
| :--- | :--- | :--- |
| `PHYSICAL_SENSOR` | Ingested autonomously from on-ground IoT hardware nodes | `deviceId`, `pilotId`, `measurements` |
| `MANUAL_ENTRY` | Logged manually by field observer / ASHA / Sarpanch | `recordedByUserId`, `pilotId`, `measurements` |
| `EXTERNAL_API` | Synchronized from state water board SCADA / CPCB servers | `sourceApiEndpoint`, `batchId` |
| `SIMULATION` | Generated by Judge Evaluation Demo engine | `isDemo: true`, `scenarioId` |

## 3. Server-Side Physical Validation & Range Bounds

The ingestion pipeline validates all incoming measurements against strict physical and thermodynamic bounds before acceptance. Payloads violating these limits are rejected immediately with `400 Bad Request`.

| Parameter | Unit | Physical Range | Rejection Criteria |
| :--- | :--- | :--- | :--- |
| **pH** | pH scale | $0.0 - 14.0$ | $\text{pH} < 0 \lor \text{pH} > 14$ |
| **Turbidity** | NTU | $0.0 - 1000.0$ | $\text{Turbidity} < 0 \lor \text{Turbidity} > 1000$ |
| **TDS** | ppm / mg/L | $0.0 - 10000.0$ | $\text{TDS} < 0 \lor \text{TDS} > 10000$ |
| **Temperature** | °C | $-20.0 - 100.0$ | $\text{Temp} < -20 \lor \text{Temp} > 100$ |
| **Clock Skew** | UTC Timestamp | $\le \text{Now} + 5\text{ mins}$ | $\text{Timestamp} > \text{ServerNow} + 300\text{s}$ (Future Clock Drift) |

## 4. BIS IS 10500:2012 Regulatory Compliance Engine

InnovateIQ continuously scores incoming water telemetry against the **Bureau of Indian Standards Drinking Water Specification (IS 10500:2012)**:

```
                                  Turbidity (NTU)
                                         │
                   Acceptable Limit      │      Permissible Limit
                       (1.0 NTU)         │          (5.0 NTU)
              ───────────────────────────┼───────────────────────────►
               [OPTIMAL]                 │ [ELEVATED - WARNING]      │ [CRITICAL VIOLATION]
               0.0 - 1.0 NTU             │ 1.1 - 5.0 NTU             │ > 5.0 NTU
                                         │                           │ (Triggers Decision Alert)
```

### Threshold Classification Matrix
| Parameter | Acceptable Limit (Desirable) | Permissible Limit (Absence of Alternate Source) | Critical Threshold |
| :--- | :---: | :---: | :---: |
| **pH** | $6.5 - 8.5$ | No Relaxation | $< 6.5 \lor > 8.5$ |
| **Turbidity** | $\le 1.0\text{ NTU}$ | $\le 5.0\text{ NTU}$ | $> 5.0\text{ NTU}$ |
| **Total Dissolved Solids (TDS)**| $\le 500\text{ mg/L}$ | $\le 2000\text{ mg/L}$ | $> 2000\text{ mg/L}$ |
| **Fluoride ($F^-$)** | $\le 1.0\text{ mg/L}$ | $\le 1.5\text{ mg/L}$ | $> 1.5\text{ mg/L}$ |
| **Nitrate ($NO_3^-$)** | $\le 45\text{ mg/L}$ | No Relaxation | $> 45\text{ mg/L}$ |

## 5. Autonomous Decision Alerts & Action Tasks

When measurements exceed critical thresholds:
1. **Anomaly Classification**: The pipeline assigns status `CRITICAL` or `WARNING`.
2. **Decision Alert Generation**: An explainable `DecisionAlert` is dispatched with:
   - **Observed Measurement**: e.g., `"Turbidity spiked to 16.2 NTU (324% above BIS permissible limit)"`.
   - **AI Interpretation**: Root cause deduction, e.g., `"Probable canal runoff infiltration or pre-filter membrane rupture"`.
   - **Recommended Action**: Actionable field steps, e.g., `"Isolate valve #4, dispatch reverse flush maintenance"`.
3. **Audit Trail**: The alert is logged to the SHA-256 tamper-evident ledger.
4. **Action Assignment**: Field engineers can acknowledge the alert and dispatch trackable operational tasks (`POST /api/actions`).
